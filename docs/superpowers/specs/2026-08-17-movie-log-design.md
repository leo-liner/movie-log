# movie-log 설계 문서

작성일: 2026-08-17

## 1. 목적

프론트엔드 엔지니어가 백엔드 역량을 기르기 위한 학습용 서비스. 학습이 목적이지만
실제로 배포되어 사용 가능한 상태를 유지한다.

만드는 것은 영화·드라마 감상 기록 소셜 서비스다. 사용자는 본 영화를 기록하고 평점과
리뷰를 남기며, 다른 사용자를 팔로우해 홈 피드에서 그들의 기록을 본다.

### 학습 목표 (우선순위 순)

1. **데이터 모델링·쿼리** — 스키마 설계, 인덱스, N+1, 트랜잭션, 마이그레이션
2. **인증·API 설계** — 세션/토큰, 권한 스코프, 공개 범위 강제, 레이트 리밋
3. **인프라·운영** — 컨테이너 배포, CI/CD, 로깅·메트릭, 캐시, 부하 테스트

비동기·메시지 큐는 이번 프로젝트의 학습 범위에서 제외한다.

### 최우선 제약: 운영 비용 0원

이 프로젝트는 **금전적 비용이 발생하지 않는 범위 안에서만** 구성한다. 이 제약이
클라우드 선택, 인스턴스 사양, 컨테이너 레지스트리, 도메인 방식을 모두 결정한다.
설계 판단이 갈릴 때는 비용 0을 우선한다.

무료 한도를 넘길 위험이 있는 항목은 9절에 모아 관리한다.

### 비목표

- 실사용자 유치, 수익화
- 마이크로서비스 분리
- 쿠버네티스 (4단계 이후 별도 과제로 남겨둠)
- 프론트엔드 완성도 — 동작 확인에 필요한 최소 화면만 만든다

## 2. 기술 스택

| 영역 | 선택 | 비고 |
|---|---|---|
| 언어 | Kotlin (JDK 25 LTS) | |
| 프레임워크 | Spring Boot 4.1 | Spring Framework 7 기반 |
| 빌드 | Gradle 9 (Kotlin DSL) | 단일 모듈로 시작 |
| ORM | Spring Data JPA + Hibernate | N+1과 영속성 컨텍스트 학습이 목적 |
| 마이그레이션 | Flyway | |
| DB | PostgreSQL 16 | 컨테이너로 직접 운영 |
| 캐시 | Redis 7 | 4단계부터 본격 사용 |
| 리버스 프록시 | Caddy | HTTPS 자동 발급·갱신 |
| 컨테이너 | Docker + Docker Compose | |
| 레지스트리 | GitHub Container Registry (GHCR) | 퍼블릭 레포지토리는 무료 |
| CI/CD | GitHub Actions | 퍼블릭 레포지토리는 실행 시간 무제한 |
| 클라우드 | Oracle Cloud Infrastructure (Always Free) | |
| 외부 API | TMDB | 영화 메타데이터 |

### 스택 선택 이유

단일 모듈로 시작하는 이유는 초반 복잡도를 낮추기 위해서다. 모듈 경계는 실제로
의존성이 꼬였을 때 나누는 편이 낫다.

JPA를 쓰는 이유는 편의가 아니라 학습이다. 지연 로딩, 영속성 컨텍스트,
`@Transactional` 전파 속성이 어떻게 동작하는지가 이 프로젝트의 주요 학습 대상이다.

**GitHub 레포지토리는 퍼블릭으로 만든다.** GHCR의 이미지 저장과 GitHub Actions의
실행 시간이 퍼블릭 레포지토리에서만 무제한 무료다. 프라이빗으로 두면 각각 500MB와
월 2,000분 한도에 걸린다.

## 3. 로드맵

각 단계는 배포 가능한 상태로 끝난다. 단계마다 반드시 만나야 할 백엔드 문제를 미리
정해두고, 그 문제가 실제로 발생하도록 데이터를 대량 생성해 재현한 뒤 해결한다.

| 단계 | 내용 | 이 단계에서 다루는 문제 |
|---|---|---|
| 0 | 프로젝트 골격 + 배포 파이프라인 | 환경별 설정 분리, 시크릿 주입, ARM64 크로스 빌드, 이미지 레이어 캐싱 |
| 1 | 인증, TMDB 검색·캐싱, 감상 기록 | 외부 데이터 복제 범위, 중복 저장 방지, 스키마 마이그레이션 |
| 2 | 팔로우, 홈 피드, 좋아요 | N+1 재현과 해결, 피드 팬아웃 전략 전환 |
| 3 | 공개 범위, 차단, API 키, 레이트 리밋 | 권한 조건 누락 방지, 토큰 버킷 |
| 4 | 연간 결산 통계, 캐시, 모니터링 | 집계 쿼리 최적화, 캐시 무효화, 부하 테스트 |

## 4. 0단계 상세 설계

기능이 거의 없는 상태에서 배포까지 관통시켜 놓는 단계다. `GET /health` 하나만 있는
애플리케이션이 실제 URL에서 응답하는 것이 완료 조건이다.

### 4.1 인프라 구성

**클라우드**: Oracle Cloud Infrastructure의 Always Free 리소스.

Always Free 리소스는 **테넌시의 홈 리전에서만** 무료다. 홈 리전은 계정을 만들 때
정하며 이후 변경할 수 없으므로, 가입 시 춘천(`ap-chuncheon-1`) 또는
서울(`ap-seoul-1`)을 선택한다. 다른 리전을 고르면 같은 리소스에 정상 요금이 붙는다.

**인스턴스**: `VM.Standard.A1.Flex` (Ampere ARM), 2 OCPU / 12GB, Ubuntu LTS.

공식 한도는 월 1,500 OCPU 시간과 9,000 GB 시간이며, 한 대를 24시간 켜두는 기준으로
2 OCPU / 12GB에 해당한다. 부트 볼륨은 50GB로 잡는다 (블록 볼륨 총 한도 200GB).

공인 IP 1개가 인스턴스에 포함되며, 아웃바운드 데이터는 월 10TB까지 무료다.

**CPU 아키텍처가 ARM64라는 점이 배포 파이프라인에 영향을 준다.** 4.4에서 다룬다.

**컨테이너 구성** (인스턴스 한 대에 전부 배치):

| 컨테이너 | 역할 | 메모리 상한 |
|---|---|---|
| `caddy` | 리버스 프록시, HTTPS | 128MB |
| `app` | Spring Boot | 4GB |
| `postgres:16` | 주 데이터베이스 | 2GB |
| `redis:7` | 캐시 | 512MB |

`app`의 상한을 4.2에서 정할 힙 크기(3GB)보다 넉넉하게 잡은 이유는, 컨테이너 메모리
사용량이 힙만이 아니기 때문이다. 메타스페이스, 스레드 스택, 다이렉트 버퍼가 힙 바깥에
따로 잡히므로 상한을 힙과 같게 두면 컨테이너가 강제 종료된다.

합계는 약 6.6GB로 12GB의 절반 정도다. 남는 용량은 2단계에서 시드 데이터를 10만 건
규모로 넣고 부하 테스트를 돌릴 때 쓴다.

**도메인·HTTPS**: sslip.io를 사용한다. `<IP를 하이픈으로 구분한 형태>.sslip.io` 가
해당 IP로 해석되는 무료 와일드카드 DNS다. Caddy가 이 도메인으로 Let's Encrypt
인증서를 자동 발급하고 만료 전에 갱신한다.

**방화벽**: OCI는 두 겹으로 막혀 있다. 클라우드 쪽의 시큐리티 리스트(또는 네트워크
시큐리티 그룹)와 인스턴스 안의 `iptables` 규칙 양쪽을 모두 열어야 접속된다. Ubuntu
이미지는 기본적으로 22번만 열려 있으므로 80·443을 양쪽에 추가한다.

SSH는 배포 파이프라인이 사용하므로 22번을 열어두되, 비밀번호 로그인을 끄고 키 인증만
허용한다.

### 4.2 유휴 인스턴스 회수 대응

Oracle은 Always Free 인스턴스가 7일 동안 다음 세 조건을 모두 만족하면 유휴로 판단해
회수할 수 있다.

- CPU 사용률 95백분위수가 20% 미만
- 네트워크 사용률 20% 미만
- 메모리 사용률 20% 미만 (A1 형태에만 적용)

세 조건이 **모두** 참일 때만 해당되므로, 하나만 깨면 된다. 메모리 조건이 가장 다루기
쉽다. 12GB의 20%는 2.4GB이므로, JVM에 `-Xms3g -Xmx3g`를 주어 힙을 시작 시점에 미리
확보하면 메모리 사용률이 항상 기준을 넘는다. Postgres의 `shared_buffers`를 함께
키우면 더 확실하다.

이 방식은 자원을 낭비하는 게 아니라 어차피 남는 12GB를 미리 잡아두는 것이므로 성능
면에서도 손해가 없다.

### 4.3 애플리케이션 골격

- `GET /health` — 상태와 함께 빌드된 커밋 해시를 반환한다. 배포된 버전이 무엇인지
  브라우저에서 바로 확인하기 위해서다. 커밋 해시는 빌드 시점에 환경 변수로 주입한다.
- 설정은 `application.yml`(공통) + `application-local.yml` + `application-prod.yml`로
  나눈다. 운영 환경의 DB 접속 정보와 API 키는 파일이 아니라 환경 변수로 주입한다.
- Flyway를 이 시점에 붙인다. 테이블이 아직 없어도 마이그레이션 도구를 먼저 도입해야
  나중에 스키마를 손으로 고치는 습관이 생기지 않는다.

### 4.4 컨테이너 이미지와 ARM64

서버가 ARM64인데 개발 머신(Apple Silicon)도 ARM64이므로 로컬 빌드는 문제없다. 문제는
GitHub Actions다. 기본 러너인 `ubuntu-latest`는 x86_64라서, 여기서 만든 이미지는
서버에서 실행되지 않는다.

두 가지 해결책이 있다.

1. **ARM 러너를 쓴다** — `ubuntu-24.04-arm` 러너는 퍼블릭 레포지토리에서 무료다.
   네이티브 빌드라 빠르다. 이 방식을 택한다.
2. QEMU 에뮬레이션으로 크로스 빌드한다 — `docker/setup-qemu-action`을 쓰면 x86
   러너에서도 ARM 이미지를 만들 수 있지만 몇 배 느리다.

이미지는 Spring Boot의 layered jar를 이용한 멀티스테이지 빌드로 만든다. 의존성
레이어와 애플리케이션 레이어를 분리하면 코드만 바뀐 커밋에서 의존성 레이어가 캐시되어
빌드와 전송이 빨라진다. 베이스 이미지는 JRE만 포함된 것을 쓴다.

### 4.5 배포 파이프라인

`main` 브랜치에 push할 때 GitHub Actions가 실행하는 순서:

1. `./gradlew test`
2. ARM64 이미지 빌드 → GHCR에 푸시 (태그는 커밋 해시)
3. SSH로 서버에 접속해 `docker compose pull && docker compose up -d`
4. `/health`가 200을 반환할 때까지 폴링. 실패하면 이전 이미지 태그로 되돌린다

**배포용 SSH 접근을 어떻게 다룰지가 이 단계의 보안 학습 지점이다.** 개인 SSH 키를
그대로 GitHub Secrets에 넣는 대신, 배포 전용 사용자와 전용 키 쌍을 따로 만들고 그
사용자가 할 수 있는 일을 최소한으로 제한한다. 키가 유출되어도 피해 범위가 서버 전체가
아니라 배포 동작으로 한정된다.

GHCR 인증은 `GITHUB_TOKEN`으로 처리되므로 별도 시크릿이 필요 없다.

### 4.6 0단계 완료 조건

`main`에 push한 뒤 몇 분 안에 `https://<ip>.sslip.io/health`가 방금 커밋의 해시를
반환한다.

## 5. 데이터 모델 (개요)

0단계에는 테이블이 없다. 아래는 1~2단계에서 만들 엔티티의 뼈대이며, 상세 컬럼은 해당
단계에 진입할 때 확정한다.

### 5.1 엔티티

- `users` — 인증 정보, 프로필, 기본 공개 범위
- `movies` — TMDB 영화 정보의 로컬 사본
- `log_entries` — 감상 기록 한 건 (본 날짜, 리뷰, 재관람 여부, 공개 범위)
- `ratings` — 사용자별 영화 평점
- `watchlist_items` — 볼 영화 목록
- `follows` — 팔로우 관계
- `likes` — 감상 기록에 대한 좋아요

### 5.2 설계 결정

**TMDB 데이터 복제 범위.** 장르·감독·배우를 전부 정규화하면 테이블이 금세 열 개를
넘는다. 반대로 응답 JSON을 통째로 저장하면 장르별 필터가 불가능해진다.

→ 검색·필터에 쓰는 필드(제목, 개봉 연도, 장르)만 컬럼으로 분리하고 나머지는 `jsonb`
컬럼 하나에 담는다. Postgres는 `jsonb`에 GIN 인덱스를 걸 수 있어서, 나중에 다른
필드로 조회가 필요해지면 그때 인덱스를 추가한다.

**평점과 감상 기록의 분리.** 같은 영화를 세 번 보면 `log_entries`에 세 행이 생긴다.
평점이 각 행에 붙어 있으면 "이 사용자가 이 영화에 매긴 점수"가 셋이 되어 평균 계산이
모호해진다.

→ 평점은 `ratings` 테이블에 `(user_id, movie_id)` 유일 제약으로 하나만 둔다.

**공개 범위 강제.** `log_entries.visibility`는 `PUBLIC` / `FOLLOWERS` / `PRIVATE`
세 값을 가진다. 이 조건은 피드·프로필·검색 등 거의 모든 조회 쿼리에 들어가야 하며,
한 군데라도 빠지면 비공개 기록이 노출된다.

→ 3단계에서 이 조건이 구조적으로 빠질 수 없게 만드는 방법을 설계한다. 후보는 조회
전용 리포지토리 계층으로 통로를 하나로 묶는 방식과 Hibernate 필터를 쓰는 방식이며,
두 방식을 비교한 뒤 결정한다.

## 6. 이후 단계 개요

### 1단계 — 인증, 영화 검색, 감상 기록

회원가입·로그인, TMDB 검색 프록시, 감상 기록 작성·수정·삭제. 검색 결과의 영화를
처음 기록할 때 `movies`에 저장하며, 이때 동시 요청으로 같은 영화가 중복 저장되지 않게
`tmdb_id`에 유일 제약을 건다.

### 2단계 — 팔로우, 홈 피드, 좋아요

이 프로젝트의 핵심 학습 지점이다.

시드 데이터를 10만 건 규모로 생성해 N+1을 실제로 재현한 뒤, `fetch join`과
`@BatchSize`로 해결하고 쿼리 수와 응답 시간의 변화를 측정한다.

홈 피드는 먼저 읽을 때 조립하는 방식(fan-out on read)으로 구현한다. 팔로우 수를
늘려가며 응답 시간이 무너지는 지점을 측정한 다음, 쓸 때 미리 뿌리는 방식
(fan-out on write)으로 전환하고 두 방식의 트레이드오프를 기록한다.

### 3단계 — 공개 범위, 차단, API 키, 레이트 리밋

5.2에서 미룬 공개 범위 강제 구조를 여기서 결정하고 적용한다. 차단한 사용자를 피드와
검색에서 제외한다. 개인 API 키를 발급하고 토큰 버킷으로 레이트 리밋을 건다.

### 4단계 — 통계, 캐시, 모니터링

연간 결산(본 편수, 장르 분포, 평점 분포)을 집계 쿼리로 만들고 실행 계획을 읽어
최적화한다. Redis 캐시를 붙이고 무효화 시점을 정한다. k6로 부하 테스트를 돌리고,
슬로우 쿼리 로그와 애플리케이션 메트릭을 확인한다.

## 7. 무료 한도 관리

비용 0을 지키기 위해 넘지 말아야 할 선과 그 근거를 모아둔다.

| 항목 | 한도 | 초과 시 |
|---|---|---|
| OCI 컴퓨트 | 월 1,500 OCPU 시간 / 9,000 GB 시간, 홈 리전 | 정상 요금 |
| OCI 블록 볼륨 | 총 200GB (부트 볼륨 포함) | 정상 요금 |
| OCI 아웃바운드 | 월 10TB | 정상 요금 |
| GHCR | 퍼블릭 레포지토리는 무제한 | 프라이빗은 500MB |
| GitHub Actions | 퍼블릭 레포지토리는 무제한 | 프라이빗은 월 2,000분 |
| TMDB API | 무료, 사용량 제한 있음 | 429 응답 |

**지켜야 할 규칙**

- 리소스는 반드시 홈 리전에 만든다. 다른 리전에 만든 블록 볼륨은 무료 대상이 아니다.
- GitHub 레포지토리를 프라이빗으로 바꾸지 않는다.
- OCI 콘솔에서 예산(Budget)을 1달러로 걸고 알림을 켠다. 실수로 유료 리소스를 만들면
  즉시 알 수 있다.
- TMDB 검색 요청을 그대로 흘려보내지 않고 로컬에 캐싱한다.

## 8. 위험 요소

**A1 인스턴스 확보 실패.** 무료 ARM 인스턴스는 수요가 많아 생성 시
"Out of capacity" 오류가 날 수 있다. 대응은 두 가지다. 시간대를 바꿔 재시도하거나,
Always Free에 함께 포함된 AMD `VM.Standard.E2.1.Micro`(1GB) 2대로 시작한 뒤 A1이
확보되면 옮긴다. 다만 1GB에서는 Postgres와 JVM을 같이 올리기 빠듯하므로 스왑이
필요하다.

**유휴 회수.** 4.2에서 다룬 방식으로 대응한다.

**sslip.io 의존.** 무료 서비스이므로 중단될 가능성이 있다. 중단되면 도메인을 사거나
다른 와일드카드 DNS로 교체한다. Caddy 설정 한 줄만 바뀌므로 영향은 작다.
